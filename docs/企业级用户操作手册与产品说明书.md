## 3. 引言

本章说明本文档的目的、读者、前置知识、覆盖范围和书写规则，确保用户按统一术语理解软件行为。

### 3.1 文档目的

本文档用于指导用户完成 FaultPolyTrace 的安装部署、初始化配置、GeoEast 集成运行、外部文件运行、参数设置、结果查看、质量检查、故障处理和日常运维。文档目标是让非研发用户也能独立完成从“输入断层属性数据”到“得到闭合断层多边形结果”的完整流程。

### 3.2 适用对象

本文档适用于以下人员：

- 构造解释人员：负责选择输入数据、设置追踪参数、查看断层多边形结果。
- 地球物理解释人员：负责判断属性响应、弱断层、交切关系和结果合理性。
- 系统管理员：负责部署软件、配置 GeoEast 路径、账号和环境变量。
- 运维人员：负责日志收集、故障排查、备份恢复和版本升级。
- 验收人员：负责核对功能、性能、质量、文档和可回溯证据。
- 开发者：负责扩展算法、命令行接口、GeoEast 集成和质量脚本。

### 3.3 前置知识

用户不需要掌握算法源码，但建议了解以下基本概念：

- 平面断层属性：二维网格中每个采样点的断层响应强度，通常数值越高越可能是断层。
- 断层多边形：围绕断层响应带生成的闭合区域，可用于解释、面积统计和后续地质分析。
- GeoEast 对象：本产品主要读取 `BOMapGrid` 网格对象，写入 `BOFaultPolygon` 多边形对象。
- 阈值和分位数：用于从连续属性图中筛选候选断层响应。

## 4. 产品概览

本章从业务视角说明 FaultPolyTrace 是什么、解决什么问题、包含哪些模块，以及数据如何在软件和 GeoEast 之间流转。

### 4.1 产品定位

FaultPolyTrace 是面向平面断层属性数据的断层多边形自动追踪系统。产品通过自动识别二维断层属性图中的线性和带状响应，生成可闭合、可统计、可叠合显示的断层多边形，减少人工拾取工作量，提高构造解释效率和一致性。

### 4.2 核心价值

- 提升效率：将人工逐条拾取断层多边形的工作转化为秒级自动追踪和复核。
- 提高一致性：使用统一参数和质量门禁，降低不同解释人员之间的主观差异。
- 支持 GeoEast 集成：可读取 GeoEast `BOMapGrid`，写回 `BOFaultPolygon`，并在平面成图中叠加查看。
- 支持外部文件：可处理 DAT、ASCII 网格和命令行批处理场景。
- 提供质量证据：输出面积、拓扑、覆盖、耗时和诊断文件，便于验收和回溯。

### 4.3 目标用户

| 用户 | 主要目标 |
|---|---|
| 构造解释人员 | 快速获得断层多边形结果并在 GeoEast 中叠合检查 |
| 地球物理解释人员 | 调整参数以兼顾弱响应召回和近邻断层分离 |
| 客户管理员 | 管理部署路径、账号权限、输出命名和数据归档 |
| 运维人员 | 保证软件、GeoEast、数据库和许可证环境可用 |
| 验收人员 | 核对赛题需求、性能指标、质量图和结果文件 |

### 4.4 核心功能清单

| 模块 | 功能 | 说明 |
|---|---|---|
| 数据读取 | GeoEast 数据库读取 | 读取指定 `BOMapGrid` |
| 数据读取 | 外部文件读取 | 支持 DAT、ASCII / 矩阵网格 |
| 自动追踪 | Ridge-Belt 追踪 | 自动生成闭合断层多边形 |

| 质量控制 | 根系防黏连 | 减少近邻断层错误合并 |
| 质量控制 | 残余弱响应复核 | 提高细弱断层召回 |
| 结果处理 | 面积统计 | 统计面积、周长、属性信息 |
| 结果处理 | 面积阈值过滤 | 按最小面积过滤小碎片 |
| 结果输出 | GeoEast 写入 | 写入 `BOFaultPolygon` |
| 结果输出 | 文件输出 | 输出 CSV、WKT、JSON、质量图 |
| 界面操作 | Qt 启动器 | 提供连接、参数、运行、日志界面 |
| 运维验收 | 质量脚本 | 生成对比图、诊断报告、性能报告 |

### 4.5 产品架构说明

【架构图占位：建议展示 Qt 启动器、GeoEast Runner、核心算法库、文件 IO、质量诊断脚本和 GeoEast 数据库之间的关系。】

架构分为四层：

1. 用户交互层：GeoEast 菜单入口、Qt 启动器、命令行入口。
2. 集成适配层：GeoEast `BOMapGrid` 读取、`BOFaultPolygon` 写入、环境变量和数据库连接。
3. 算法核心层：阈值分割、骨架追踪、分支剪枝、断点补连、防黏连、闭合多边形生成、平滑简化、拓扑诊断。
4. 交付支撑层：质量评估脚本、报告生成脚本、性能回归脚本、文档和发布包。

### 4.6 业务流程说明

【流程图占位：建议展示“选择输入网格 -> 选择参数预设 -> 执行追踪 -> 写入结果 -> 叠合检查 -> 质量报告归档”的流程。】

标准业务流程如下：

1. 用户在 GeoEast 中准备或导入平面断层属性网格。
2. 用户打开 FaultPolyTrace 启动器。
3. 用户配置数据库、项目、账号、输入网格和输出名称。
4. 用户选择算法预设和必要参数。
5. 用户点击【开始追踪】。
6. 系统读取网格、执行算法、生成闭合多边形。
7. 系统写入 GeoEast 数据库或外部文件。
8. 用户在 GeoEast 平面成图中叠加查看原始属性和结果多边形。
9. 用户根据质量诊断结果决定是否接受、复跑或调整参数。

### 4.7 模块关系说明

| 模块 | 上游输入 | 下游输出 |
|---|---|---|
| Qt 启动器 | 用户输入、环境变量、配置文件 | Runner 参数 |
| GeoEast Runner | GeoEast 数据库、命令行参数 | `BOFaultPolygon`、日志 |
| 核心算法库 | `Grid2D` 网格、追踪参数 | 多边形集合、诊断信息 |
| 文件 IO | DAT / ASCII / CSV / JSON | 外部结果文件 |
| 质量脚本 | 原始网格、结果 CSV、诊断 JSON | 对比图、质量报告 |

### 4.8 数据流说明

GeoEast 集成数据流：

```text
GeoEast BOMapGrid -> GeoEast Runner -> 核心算法 -> BOFaultPolygon -> GeoEast 平面成图叠合显示
```

外部文件数据流：

```text
DAT / ASCII 网格 -> faultpolytrace.exe -> CSV / WKT / diagnostics.json -> 质量图和报告
```

| 部署形态 | 说明 | 适用场景 |
|---|---|---|
| GeoEast 本地集成 | 部署到 `GeoEast-RC\bin` 并添加菜单入口 | 正式演示、生产解释 |
| Qt 启动器本地运行 | 独立启动 `faultpolytrace_launcher.exe` | 日常运行、参数调整 |
| 命令行运行 | 使用 `faultpolytrace.exe` 或 Runner 参数运行 | 批处理、回归测试 |
| 离线质量评估 | 使用脚本生成质量图和报告 | 验收、答辩、研发复核 |

### 4.10 适用场景和不适用场景

适用场景：

- 沿层断层属性、断层概率、相干、曲率、蚂蚁体等二维网格。
- 断层响应呈线性、带状、分支或交切形态。
- 需要闭合多边形、面积统计、面积过滤和 GeoEast 展示的解释场景。

不适用场景：

- 输入不是规则二维网格。
- 坐标、采样间隔或网格头信息严重错误。
- 属性高低值含义不明确，无法判断高值是否表示断层。
- 需要三维体断层面建模但没有平面属性切片。

### 4.11 产品限制和边界

FaultPolyTrace 输出的是基于平面属性的自动追踪建议结果，不替代解释人员对地质背景、层位关系和断层性质的最终判断。对于极弱响应、数据缺失、强噪声或复杂交切区，建议结合原始地震、解释层位和人工复核。

## 7. 登录、账号与权限

本章说明 FaultPolyTrace 与 GeoEast 账号体系的关系，以及不同用户需要具备的权限。

### 7.1 登录入口

用户先登录 GeoEast，再通过 GeoEast 菜单入口或本地启动器打开 FaultPolyTrace。FaultPolyTrace 本身不提供独立账号中心。

### 7.2 首次登录流程

| 账号类型 | 说明 |

### 7.10 账号创建、停用、删除、锁定、解锁流程

账号生命周期由 GeoEast 或企业账号系统管理。FaultPolyTrace 不创建、停用或删除账号。若用户无法连接数据库，应先确认账号是否过期、锁定、无项目权限或密码错误。

### 7.11 登录日志和权限变更审计

FaultPolyTrace 日志记录运行用户、数据库、项目、输入对象、输出对象、参数和运行结果。账号登录日志、权限变更日志由 GeoEast 或企业账号系统记录。审计时应同时收集启动器日志、Runner 日志、GeoEast 日志和数据库权限变更记录。

### 9.11 使用命令行批处理

功能名称：使用命令行批处理  
功能说明：通过命令处理外部文件或批量回归。  
适用角色：开发者、运维人员、技术评审。

4. 执行命令行程序。
5. 查看输出 CSV 和诊断 JSON。
6. 可选：运行质量评分脚本。

```powershell
.\build\faultpolytrace.exe `
  --input .\examples\data\test.dat `
  --output .\examples\outputs\run_20260523\polygons.csv `
  --trace-mode ridge-belt `
  --threshold-mode percentile `

  --min-area 120 `
  --simplify-tolerance 2 `
  --smooth-iterations 1
```

### 10.7 生效机制

### 10.8 风险提示

警告：提高召回类参数可能增加碎片或黏连风险；增强防黏连类参数可能切断本应连接的弱响应。正式交付前必须生成质量图和拓扑诊断。

### 10.9 回滚方式

如参数调整导致结果变差，按以下方式回滚：

1. 保留异常输出目录。
2. 切回【贴合融合推荐】预设。
3. 使用新的输出对象名重新运行。
4. 对比基线和异常结果。
5. 删除或标记异常结果，不作为正式成果。

## 12. 报表、查询与分析

本章说明如何理解输出统计、质量指标、图表和常见数据口径问题。

### 12.1 查询条件说明

常见查询条件包括输出对象名、运行时间、输入网格名、参数预设、最小面积、拓扑结果和质量评分。

### 12.2 筛选规则

| 筛选项 | 规则 |
|---|---|
| 面积过滤 | 面积小于 `--min-area` 的多边形标记为过滤 |
| 拓扑过滤 | 开放环、自相交、异常相交结果不得作为正式交付 |
| 质量复核 | 强响应、弱响应、黏连风险和粒度共同评价 |

### 12.3 报表类型

| 报表 | 说明 |
|---|---|
| 面积统计表 | 每个多边形面积、周长和保留状态 |
| 拓扑诊断表 | 开放环、自相交、异常相交明细 |
| 分支诊断表 | 骨架分支长度、强度、剪枝状态 |
| 质量评分报告 | 覆盖、防黏连、粒度、拓扑、性能综合评分 |
| 对比图 | 原始属性和结果多边形叠合 |

### 12.4 指标口径

| 指标 | 口径 | 推荐目标 |
|---|---|---|
| 强响应覆盖率 | 高属性断层响应被多边形覆盖比例 | 越高越好，推荐不低于 99% |
| 弱响应覆盖率 | 细弱断层响应被多边形覆盖比例 | 越高越好，推荐不低于 95.5% |
| 高风险黏连 | 可能把不同脉络断层合成大圈的对象 | 越少越好 |
| 开放环 | 未闭合多边形数量 | 必须为 0 |
| 自相交 | 自身边界交叉的多边形数量 | 必须为 0 |
| 异常相交 | 不同多边形异常相交数量 | 必须为 0 |
| 核心耗时 | 算法核心处理时间 | 小于 60 秒，推荐秒级 |

### 12.5 数据刷新频率

启动器运行完成后立即刷新日志和结果信息。GeoEast 平面成图可能需要重新加载对象或刷新数据集管理器才能看到新结果。

### 12.6 导出说明

导出结果应包含：

1. 输入网格对象名。
2. 输出多边形对象名。
3. 参数预设和完整参数。
4. 结果 CSV。
5. 诊断 JSON。
6. 白底叠合图。
7. 质量报告。

### 12.7 常见数据口径问题

| 问题 | 解释 |
|---|---|
| 多边形数量不是固定值 | 数量受阈值、面积过滤、防黏连和数据质量影响，不应作为唯一标准 |
| 细弱线没有全部覆盖 | 可能是弱响应低于阈值、断续过长或被面积过滤 |
| 多边形与线之间有空隙 | 可能是平滑简化、线宽显示或坐标显示比例造成，应查看高倍叠合图 |
| 结果看起来断断续续 | 可能是断层响应本身断续、面积阈值过高或防黏连过强 |

## 14. 系统管理与运维维护

本章面向管理员和运维人员，说明日常维护、日志、监控、备份、容量和高可用建议。

### 14.1 服务启动、停止、重启

FaultPolyTrace 是任务型程序，不是常驻服务。启动、停止和重启方式见 6.6。

### 14.2 服务状态检查

| 检查项 | 方法 |
|---|---|
| 启动器状态 | 打开启动器，确认无 DLL 缺失 |
| Runner 状态 | 执行 `--help` 或 `--list-grids` |
| GeoEast 状态 | 打开 GeoEast 并进入项目 |

### 14.3 监控指标

| 指标 | 建议阈值 |
|---|---|
| 单次核心耗时 | 小于 60 秒 |

| 日志 | 路径 | 级别 | 建议保留 |
|---|---|---|---|

| Runner 控制台日志 | 控制台或启动器日志区域 | INFO / ERROR | 项目周期内 |
| 诊断 JSON | 输出文件旁 | 结构化诊断 | 与结果同周期 |
| 质量报告 | 时间戳输出目录 | 验收证据 | 与交付包同周期 |
| GeoEast 日志 | GeoEast 环境目录 | 平台日志 | 按企业制度 |

### 14.5 告警配置

当前版本不提供自动告警。建议在批处理脚本中对以下情况进行人工告警：

- 退出码非 0。
- 开放环、自交或异常相交不为 0。
- 核心耗时超过 60 秒。
- 输出多边形数量异常暴涨或异常减少。
- 结果文件未生成。

### 14.6 备份恢复

备份策略见第 11.6 节。恢复时优先恢复 GeoEast 数据库对象，其次使用结果 CSV / WKT 重新导入或重新运行。

### 14.7 性能优化

建议：

1. 使用 SSD 保存输入、输出和质量图。
2. 避免在网络盘上直接批量生成大量 PNG。
3. 批处理时限制并发。
4. 优先使用预设参数，不做大范围无目的扫描。
5. 对超大网格先做数据范围和空值检查。

### 14.8 容量规划

正式项目建议按以下规则规划：

- 每次正式运行保留完整输出。
- 每个参数实验使用独立时间戳目录。
- 每周清理明显失败的临时图像，但保留关键日志。

## 15. 安全、合规与审计

本章说明产品在身份、权限、数据、审计和高风险操作方面的安全要求。

### 15.1 身份认证

FaultPolyTrace 依赖 GeoEast 或企业账号体系进行认证。用户应使用个人账号，不建议多人共用同一账号。

### 15.2 权限控制

权限控制遵循 GeoEast 项目权限和 Windows 文件权限。业务用户只应访问授权项目和输出目录。

### 15.3 最小权限原则

为解释人员授予读取输入和写入结果权限即可，不应授予部署目录修改权限。为运维人员授予部署和日志权限即可，不应默认授予业务数据删除权限。

### 15.4 登录审计

登录审计由 GeoEast 或企业账号系统记录。FaultPolyTrace 记录运行用户和任务上下文。

### 15.5 操作审计

应记录以下信息：

- 运行时间。
- 操作用户。
- 输入网格。
- 输出对象。
- 参数预设。
- 关键参数。
- 运行结果。
- 诊断文件路径。

### 15.6 数据导出审计

外部导出 CSV、WKT、PNG 或报告时，应记录导出人、导出时间、导出路径和用途。

### 15.7 配置变更审计

配置变更包括启动器 INI 文件变更、环境变量变更、部署路径变更和脚本版本变更。正式环境建议在版本库或发布记录中保留变更说明。

### 15.8 数据加密

产品不内置加密引擎。数据加密应依赖企业磁盘加密、数据库加密、访问控制和备份加密。

### 15.9 数据脱敏

对外展示截图或报告前，应检查项目名、坐标范围、用户名、路径和敏感工区信息。

### 15.10 隐私保护

产品主要处理地质和解释数据，不主动采集个人隐私信息。日志中可能包含用户名和本机路径，应按内部资料管理。

### 15.11 合规要求

企业应用时应遵守：

- 企业数据安全制度。
- GeoEast 软件许可和使用协议。
- 项目保密协议。
- 数据出境和外发审批要求。

### 15.12 高风险操作说明

| 操作 | 风险 | 控制措施 |
|---|---|---|
| 覆盖已有结果对象 | 丢失正式解释成果 | 使用新输出名，覆盖前备份 |
| 删除结果对象 | 无法复查 | 删除前审批并导出备份 |
| 外发原始网格 | 泄露工区信息 | 脱敏和审批 |
| 使用错误许可证 | GeoEast 模块不可用 | 核对年份、版本和产品线 |
| 修改核心参数 | 结果质量波动 | 保留基线并做对比报告 |

### 15.13 安全最佳实践

- 使用个人账号运行。
- 不保存明文密码。
- 按项目建立输出目录。
- 每次正式运行保留诊断 JSON。
- 对外只提交脱敏报告。
- 发布前执行质量检查清单。

## 16. 升级、迁移与回滚

本章说明版本升级、数据迁移和回滚流程，降低升级对生产使用的影响。

### 16.1 版本兼容说明

FaultPolyTrace V1.0.0 面向当前 GeoEast-RC 集成环境和本地命令行环境。升级前应确认 GeoEast、Qt、Visual Studio 运行库和 NGP 动态库版本兼容。

### 16.2 升级前检查

1. 备份旧版本程序。
2. 备份 `faultpolytrace_launcher.ini`。
3. 备份正式输出对象和质量报告。
4. 记录当前 GeoEast 版本和许可证状态。
5. 执行基线性能回归。

### 16.3 升级影响说明

升级可能影响：

- 默认参数预设。
- 输出对象样式。
- 诊断 JSON 字段。
- 质量评分脚本口径。
- 运行耗时和多边形数量。

### 16.4 升级步骤

1. 关闭 GeoEast 和启动器。
2. 备份旧版本文件。
3. 部署新版本文件。
4. 打开启动器。
5. 使用基线数据运行一次。
6. 对比旧版本质量报告。
7. 确认无异常后启用新版本。

### 16.5 升级验证

验证项：

- 启动器可打开。
- 网格可刷新。
- Runner 可读取和写入。
- 输出多边形拓扑为 0 异常。
- 质量图与旧版本相比没有明显退化。
- 核心耗时满足性能门禁。

### 16.6 数据迁移

输出结果为 GeoEast 对象或标准文件，无需复杂迁移。升级前后的结果建议使用不同对象名保存。

### 16.7 回滚条件

出现以下情况应回滚：

- 无法读取 GeoEast 网格。
- 无法写入 `BOFaultPolygon`。
- 拓扑异常不为 0。
- 主要断层明显漏检。
- 近邻断层大面积误合并。
- 性能明显退化并超过门禁。

### 16.8 回滚步骤

1. 关闭 GeoEast 和启动器。
2. 恢复旧版本程序。
3. 恢复旧版配置文件。
4. 使用基线数据运行验证。
5. 标记新版本问题并保留日志。
6. 通知项目负责人。

### 16.9 已知问题

| 问题 | 说明 | 规避方式 |
|---|---|---|
| GeoEast 许可证年份不匹配 | 平面成图模块不可用 | 使用与软件版本匹配的许可证 |
| 手动导入 DAT 坐标异常 | 显示范围不正确 | 使用标准 ASCII 转换流程 |
| 过强防黏连导致碎片 | 弱响应可能被切断 | 使用质量图和差异诊断复核 |

### 16.10 版本变更记录

版本变更应记录功能、参数、质量指标、性能指标、已知问题和回滚方案。建议同步更新 `发布说明与验收清单.md`。

## 17. 故障排查、错误码与 FAQ

本章提供常见问题的排查流程、错误码和处理方式。

### 17.1 故障排查总流程

1. 记录现象和截图。
2. 保存启动器日志。
3. 确认输入网格、输出对象和参数。
4. 检查 GeoEast、数据库、许可证和路径。
5. 查阅错误码表。
6. 使用基线预设复跑。
7. 如仍失败，提交工单并附日志、诊断文件和复现步骤。

### 17.2 常见问题列表

| 问题 | 处理建议 |
|---|---|
| 平面成图不可用 | 核对许可证年份、模块和安装目录 |
| 网格列表不刷新 | 检查数据库、项目、账号和 `hostname.pg` |
| 结果显示很小或很大 | 核对网格坐标和采样间隔 |
| 多边形颜色看不清 | 调整结果颜色和线宽 |
| 结果断断续续 | 检查弱响应参数、面积阈值和输入属性质量 |
| 结果误合并 | 启用【防黏连增强】，并生成差异诊断 |
| 输出对象找不到 | 刷新 GeoEast 数据集管理器或确认写入项目 |

### 17.3 错误码表

| 错误码 | 错误提示 | 可能原因 | 处理方式 | 是否联系支持 |
|---|---|---|---|---|
| FPT-1001 | Runner 不存在 | 启动器配置路径错误 | 重新选择 `faultpolytrace_geoeast_runner.exe` | 否 |
| FPT-1002 | 无法刷新网格 | 数据库、项目或账号错误 | 核对连接配置和权限 | 视情况 |
| FPT-1003 | 平面成图无许可证 | 许可证年份或模块不匹配 | 替换匹配许可证并重启 | 否 |
| FPT-1004 | `hostname.pg` 不存在 | GeoEast PostgreSQL 支撑文件缺失 | 修复 NGP 支撑目录 | 是 |
| FPT-2001 | 输入网格为空 | 对象名错误或数据无有效值 | 校验 `BOMapGrid` | 否 |
| FPT-2002 | 网格坐标异常 | DAT 导入参数错误 | 使用标准 ASCII 转换 | 否 |
| FPT-3001 | 拓扑异常 | 参数过强或数据异常 | 回退预设并复跑 | 是 |
| FPT-3002 | 多边形过度黏连 | 近邻断层被错误合并 | 启用防黏连增强 | 否 |
| FPT-3003 | 多边形过碎 | 阈值过高或面积阈值过低 | 使用均衡预设 | 否 |

| FPT-5001 | bad allocation | GeoEast 环境、数据异常或内存不足 | 校验环境和输入，保留日志 | 是 |

### 17.4 登录问题排查

1. 确认 GeoEast 账号可登录。
2. 确认账号未锁定或过期。
3. 确认密码正确。
4. 确认账号有目标项目权限。
5. 让管理员检查 GeoEast 登录日志。

### 17.5 权限问题排查

### 17.6 数据问题排查

重点检查：

- 行列数是否正确。
- 坐标范围是否正确。
- 采样间隔是否正确。
- 非零像元数量是否合理。
- 高值是否代表断层响应。

### 17.7 网络问题排查

远程数据库场景需检查数据库地址、端口、防火墙和网络连通性。本地场景重点检查 GeoEast 支撑文件和环境变量。

### 17.8 数据库问题排查

运行 `--list-grids` 验证数据库连接。若列表为空，检查项目名、账号权限和数据库服务状态。

### 17.9 接口问题排查

命令行失败时，检查参数是否缺失、路径是否含特殊字符、输出目录是否存在、输入文件是否可读。

## 18. 最佳实践与典型场景

本章给出推荐配置、权限模型、业务流程、安全策略、备份策略和典型案例，帮助用户稳定获得高质量结果。

### 18.1 推荐配置

首次运行建议使用【贴合融合推荐】。若检查到明显近邻断层黏连，再使用【防黏连增强】复跑。不要把某一次测试得到的多边形数量作为唯一目标。

### 18.2 推荐权限模型

解释人员具备读取输入和写入新输出的权限；客户管理员负责输出对象命名规范和删除审批；运维人员负责部署和环境维护；验收人员使用只读账号查看结果和报告。

### 18.3 推荐业务流程

1. 准备输入网格。
2. 使用默认推荐预设运行。
3. 生成白底叠合图。
4. 检查主断层覆盖、弱响应覆盖和黏连。
5. 必要时启用防黏连或弱响应预设。
6. 生成质量报告。
7. 在 GeoEast 中保存最终结果。
8. 归档输入、输出、参数、报告和截图。

### 18.4 推荐安全策略

- 使用个人账号。
- 输出命名带项目、日期和版本。
- 正式结果只由客户管理员删除。
- 对外截图脱敏。
- 发布包和文档统一归档。

### 18.5 推荐备份策略

| 对象 | 备份周期 | 说明 |
|---|---|---|
| 输入网格 | 正式运行前 | 保证可重跑 |
| 输出对象 | 每次正式运行后 | 保证可恢复 |
| 诊断报告 | 每次正式运行后 | 保证可验收 |
| 发布包 | 每次发布后 | 保证可回滚 |
| 文档 | 每次发布后 | 保证版本一致 |

### 18.6 推荐运维周期

每次演示前检查许可证、GeoEast、数据库和输入网格。每次发布前执行烟囱测试、性能回归、Qt 启动器构建和 GeoEast Runner 构建。

### 18.7 典型业务案例

案例 1：官方赛题数据处理。  
输入 `test7_fault_attribute_bo`，使用【贴合融合推荐】或【防黏连增强】，输出 `FaultPolyTrace_Result_Check`，在平面成图中叠加原始属性和结果多边形，并生成质量报告。

案例 2：近邻断层容易黏连的数据。  
先使用【贴合融合推荐】运行，若出现不应合并的大圈，切换到【防黏连增强】，比较两版结果中是否减少跨背景或跨脉络合并。

案例 3：弱断层容易漏检的数据。  
先使用【弱响应高召回】运行，检查是否提升细弱线覆盖；若碎片明显增加，再提高面积阈值或回到均衡预设。

### 18.8 常见错误做法及风险

| 错误做法 | 风险 | 正确做法 |
|---|---|---|
| 只追求多边形数量固定 | 忽视漏检和黏连 | 用覆盖、拓扑、粒度和解释合理性综合评价 |
| 多个参数同时大改 | 无法追溯问题原因 | 每次只调整一类参数 |
| 使用红色结果线叠加红色背景 | 看不清结果 | 使用高对比颜色 |
| 不保存诊断文件 | 无法验收和复盘 | 每次正式运行归档 JSON 和报告 |
| 直接导入 DAT 不核对坐标 | 显示范围错误 | 使用标准导入流程 |

## 20. 逐章内容写作要点、推荐表格和示例文案

本章面向文档编写、评审和后续维护人员，说明本文档每一章的写作目的、应表达的核心观点、推荐使用的表格或图示，以及可以直接复用的示例文案。本章的作用类似正式产品手册的编写规范：当软件版本升级、界面变化、算法参数增加或交付对象变化时，维护人员可按照本章要求扩写、修订和审核文档，保证文档既有企业级规范，又有足够的业务解释力。

与普通操作手册不同，FaultPolyTrace 的用户既包括软件操作人员，也包括地球物理解释人员、竞赛评审人员和技术验收人员。因此文档不能只写“点击哪里”，还必须解释“为什么这样做”“结果应该如何判断”“异常现象背后的可能原因是什么”。尤其是断层多边形自动追踪类产品，输出结果具有专业解释属性，用户需要理解结果不是简单图形，而是由输入属性、阈值、断层带宽度、分支归属、拓扑约束和质量门禁共同决定的解释成果。文档应在可操作性和专业可信度之间取得平衡：前半部分让用户能独立上手，后半部分让评审和运维能复核质量、追溯过程和处理异常。

### 20.1 第 1 章“文档治理信息”写作要点

本章应回答“这份文档是谁发布的、适用于哪个版本、是否可以作为正式交付依据”。企业级产品说明书必须把文档治理放在前面，因为交付、验收、审计和后续维护都依赖清晰的版本边界。如果缺少文档版本、产品版本、发布日期、保密等级和审批记录，用户很难判断当前手册是否适用于自己安装的版本，也无法在问题回溯时确认依据。

写作时应避免使用临时沟通语气，例如“我做了什么”“你接下来做什么”。正式交付文档应以产品和用户任务为中心，使用稳定表达，例如“用户应”“系统将”“管理员需确认”。如果项目处于竞赛或试运行阶段，也应按正式软件交付标准描述，不能把文档写成聊天记录或开发日志。

推荐表格包括封面信息表、版本历史表、审批记录表、相关文档清单和技术支持联系方式表。版本历史表不应只写“更新文档”，而应说明新增了哪些章节、修正了哪些操作、影响哪些用户。审批记录可在竞赛阶段保留占位，但字段必须完整，以便后续转为正式签署版。

示例文案：

“本文档适用于 FaultPolyTrace V1.0.0 的本地部署环境、GeoEast 集成环境、Qt 启动器和命令行运行方式。若用户使用的程序版本、GeoEast 版本或数据库环境与本文档描述不一致，应优先核对发布说明和部署记录，再执行生产数据处理。”

### 20.2 第 2 章“目录与导航”写作要点

本章应解决“不同读者如何快速找到自己需要的内容”。企业级手册通常很长，如果没有角色路径和场景导航，用户容易从第一页线性阅读，效率很低。FaultPolyTrace 的读者差异较大：解释人员关注如何运行和看图，管理员关注部署和权限，评审人员关注赛题需求、质量标准和证据链，开发者关注接口和扩展。因此本章必须提供按角色和按场景的双重导航。

Word 文档应使用真实标题样式，而不是手工加粗的假标题。这样用户才能使用导航窗格、自动目录和 PDF 书签。图目录和表目录可以在 Markdown 中以清单方式维护，在 Word 中可通过题注和交叉引用进一步增强。由于当前项目还在持续优化算法和界面，截图占位必须明确写出应放置的界面或图像，避免后续补图时遗漏关键证据。

推荐表格包括角色阅读路径表、场景快速导航表、图目录和表目录。场景导航应优先覆盖真实高频任务，例如“第一次运行官方数据”“结果显示范围异常”“结果误合并”“生成验收报告”。不要只列模块名，而要从用户想完成的事情出发。

示例文案：

“如果用户只需要完成一次标准处理，可直接阅读第 8 章快速入门和第 9 章功能操作说明；如果用户需要判断结果是否达到生产级质量，应继续阅读第 12 章指标口径和第 18 章最佳实践；如果运行失败，应按第 17 章故障排查总流程收集日志、截图和诊断文件。”

### 20.3 第 3 章“引言”写作要点

引言的核心不是重复产品广告，而是建立共同语言。对于断层多边形自动追踪，很多用户可能第一次接触“平面断层属性”“分位数阈值”“弱响应”“防黏连”“拓扑诊断”等概念。文档应先用非专业用户也能理解的语言解释：输入是一张表示断层可能性的二维属性图，输出是围绕断层响应带形成的闭合多边形，系统的任务是在尽量覆盖真实断层响应的同时避免把不同断层错误连在一起。

本章还要明确文档范围。范围说明非常重要，因为 FaultPolyTrace 依赖 GeoEast，但并不替代 GeoEast 官方手册；产品能生成自动追踪结果，但不替代解释人员的最终地质判断；产品能读写 GeoEast 数据库，但不负责企业账号体系和许可证采购。边界写清楚，后续支持和验收就不会混淆。

推荐表格包括术语表、格式约定表和标识说明表。格式约定要贯穿全文，例如按钮统一写成【开始追踪】，字段统一写成“输入网格”，命令统一使用等宽字体。这样 Word、PDF、HTML 三种形态都能保持一致。

示例文案：

“本文档面向最终用户编写，不要求读者理解 C++ 源码实现。但为了正确判断输出质量，建议用户理解三个基本概念：属性值越高通常表示断层响应越强；断层多边形必须是闭合区域；结果质量不能只看多边形数量，而应综合查看覆盖、边界贴合、拓扑合法和防误合并效果。”

### 20.4 第 4 章“产品概览”写作要点

产品概览应从业务痛点切入。赛题背景中明确指出，传统方式要么依赖已经解释好的层位和断层，要么需要人工在平面断层属性上手工拾取，效率和一致性都不足。FaultPolyTrace 的定位正是把平面断层属性上的线性响应自动转化为断层多边形，从而提升构造解释自动化水平。

本章需要写清产品的核心价值：不是简单把黑线描红，而是自动完成数据读取、候选断层响应识别、分支追踪、断层带构建、闭合多边形生成、面积统计、面积过滤、质量诊断和 GeoEast 写回。对于评审而言，4.4 核心功能清单应能直接对应赛题评分项；对于用户而言，4.6 业务流程应能解释从输入到输出的完整路径。

架构图建议采用四层结构：用户交互层、集成适配层、算法核心层、交付支撑层。流程图建议采用任务流：准备数据、选择输入、配置参数、运行追踪、写入结果、叠合检查、质量归档。图中应明确 `BOMapGrid` 和 `BOFaultPolygon`，因为这两个对象是 GeoEast 集成评分的核心证据。

推荐表格包括核心功能清单、模块关系表、部署形态表、适用和不适用场景表。段落中应强调产品的泛化目标：算法不是为官方 `test.dat` 写死，而是面向规则二维平面断层属性网格设计，参数预设和质量评价机制用于适配不同数据质量和断层形态。

示例文案：

“FaultPolyTrace 的核心输出不是一张展示图，而是一组具备空间坐标、闭合边界、面积统计和拓扑诊断信息的断层多边形对象。用户可在 GeoEast 中将其与原始断层属性叠合查看，也可导出为 CSV / WKT / JSON 进行质量评估和结果归档。”

### 20.5 第 5 章“系统要求与兼容性”写作要点

系统要求章节要写得可检查、可执行，不要只写“需要较好配置”。硬件要求应分最低、推荐和高性能三档，软件要求应列出 Windows、GeoEast、Qt、Visual Studio、Python 等依赖。由于 GeoEast 环境较复杂，文档必须强调 GeoEast-RC、NGP、数据库、动态库和许可证之间的匹配关系。

兼容性说明还应覆盖网络、端口、权限和容量。很多运行失败并不是算法问题，而是 `hostname.pg` 缺失、数据库端口不可用、许可证年份不匹配、DLL 路径未配置、项目账号没有写权限等环境问题。把这些问题放在系统要求章节，可以帮助用户在安装前发现风险。

性能基线是赛题评分重点。文档应明确官方要求为核心算法 1 分钟内完成，同时给出项目内部更严格的工程目标，例如秒级处理、拓扑异常为 0、强弱响应覆盖达到推荐门槛。性能基线不能写成绝对承诺，因为不同数据规模、机器配置和数据库写入速度会影响总耗时；更合适的表达是“官方测试规模下的参考基线”和“正式验收时应以本机报告为准”。

推荐表格包括硬件要求表、软件依赖表、权限要求表、性能基线表和不兼容说明表。对于不兼容说明，应明确提醒不要混用不同年份许可证、不同 GeoEast 产品线目录和错误导入的 DAT 网格。

示例文案：

“如果用户能够成功打开 GeoEast，但无法打开平面成图模块，通常应优先检查许可证，而不是检查 FaultPolyTrace 算法。FaultPolyTrace 负责生成结果对象，但结果在 GeoEast 中的叠合显示依赖 GeoEast 平面成图模块和对应许可。”

### 20.6 第 6 章“安装、部署与初始化”写作要点

安装章节应采用步骤化写法，但每组步骤前后要有解释性段落。用户需要知道为什么要关闭 GeoEast、为什么要部署到 `GeoEast-RC\bin`、为什么要先运行环境检查、为什么部署后还要验证网格刷新和结果写入。正式手册中，安装步骤不能只写命令，还要写前置条件、预期结果和失败后的处理入口。

由于产品支持 GeoEast 集成、Qt 启动器和命令行运行，安装章节应把三类入口说明清楚。GeoEast 集成适合业务用户，Qt 启动器适合交互参数调整，命令行适合批处理和回归验证。当前版本不支持 SaaS、Docker、Kubernetes，应明确写“不适用”，避免评审或客户误以为遗漏部署方式。

部署前检查清单和部署完成检查清单是企业级交付的关键。前者防止用户在环境不满足时强行安装，后者证明安装确实可用。检查项应覆盖 GeoEast、许可证、数据库、账号、输入网格、输出权限和文件权限。

推荐表格包括安装包说明、初始化配置、安装问题处理和检查清单。若后续生成 Word 文档，部署步骤适合使用编号列表，检查清单适合使用表格。

示例文案：

“部署完成不等于软件可用。正式验收前必须至少完成一次从刷新网格、选择输入、运行追踪、写入输出到 GeoEast 叠合显示的闭环验证。只有这个闭环通过，才能说明部署、权限、数据库读写和显示链路均已打通。”

### 20.7 第 7 章“登录、账号与权限”写作要点

本章要把 FaultPolyTrace 与 GeoEast 权限体系的关系讲清楚。产品本身不提供独立账号中心，也不负责创建用户、停用用户或配置 LDAP。它通过 GeoEast / NGP 环境访问数据库，因此实际认证和项目权限由 GeoEast 或企业账号系统控制。这样的说明能避免用户在 FaultPolyTrace 中寻找不存在的“用户管理页面”。

权限矩阵要覆盖读取、写入、覆盖、删除、部署和查看日志等操作。对解释人员而言，通常只需要读取输入和写入新输出；对管理员而言，需要部署和配置权限；对验收人员而言，通常只需要只读查看和导出报告。高风险操作如覆盖已有结果、删除结果对象，必须有审批或备份说明。

登录日志和权限变更审计也要区分责任边界。FaultPolyTrace 可记录运行上下文，但账号登录和权限变更一般由 GeoEast 或企业账号系统记录。审计时需要合并多方日志。

推荐表格包括账号类型表、权限矩阵、账号生命周期说明和审计字段表。正文应强调最小权限原则。

示例文案：

“建议正式生产环境中为解释人员授予读取输入网格和写入新结果对象的权限，但不默认授予删除正式成果或修改部署目录的权限。这样既能保证日常解释效率，也能减少误删、误覆盖和环境被意外修改的风险。”

### 20.8 第 8 章“快速入门”写作要点

快速入门必须让用户在短时间内完成一个完整闭环。它不是参数百科，也不是算法讲解，而是一个最小可行任务：打开启动器、连接 GeoEast、选择输入、设置输出、选预设、运行、在 GeoEast 中叠合查看。每一步都要写清用户点击哪里、填写什么、看到什么。

对于 FaultPolyTrace，快速入门的核心价值是让用户第一次看到“原始平面断层属性”和“自动追踪结果”叠合在一起。只有看到叠合图，用户才会理解产品输出的实际形态。快速入门中应提醒用户选择高对比颜色，尤其当原始属性背景为红色时，结果线不宜也用红色。

快速入门的输出对象名建议带 `QuickStart` 或日期后缀，避免覆盖正式成果。预设建议使用【贴合融合推荐】，如果用户已知近邻黏连问题，再提示可选【防黏连增强】。不要在快速入门中过多解释每个参数，否则会破坏 5 到 10 分钟上手目标。

推荐表格包括任务说明、前置条件、示例字段值和预期结果。正文应包含“下一步阅读建议”，引导用户进入参数、质量和故障章节。

示例文案：

“完成快速入门后，用户应至少得到三个结果：GeoEast 数据库中的一个输出多边形对象、启动器日志中的运行成功信息，以及一张原始属性与结果多边形的叠合画面。如果三者缺一，说明闭环尚未完全打通。”

### 20.9 第 9 章“功能操作说明”写作要点

功能操作章节是用户手册的主体，应采用统一模板。每个功能都要包含功能名称、功能说明、适用角色、权限要求、前置条件、入口路径、使用场景、操作步骤、字段说明、输入规则、预期结果、注意事项、常见问题、异常处理、审计记录、相关功能和截图占位。这种模板看起来较长，但能保证用户遇到问题时不必跨章节拼信息。

操作步骤必须“一步一个动作”。例如不要写“填写数据库、项目、用户并刷新网格”，而应拆成四步。这样用户能按步骤执行，文档也更适合培训和验收。按钮、菜单、字段、命令、路径格式必须统一。

对于本产品，功能章节必须覆盖启动器、连接配置、刷新网格、导入外部文件、输出对象命名、颜色和线宽、算法预设、参数调整、开始追踪、GeoEast 叠合查看、面积统计、质量诊断、命令行批处理和质量报告生成。每个功能应说明常见异常，例如网格范围异常、许可证不可用、颜色不明显、拓扑异常、结果误合并等。

推荐表格包括字段说明表、预设适用场景表、异常处理表。截图占位应明确，例如“启动器主界面”“连接配置区域”“输入网格下拉框”“GeoEast 叠合图”。

示例文案：

“当用户发现结果中出现大圈式误合并时，不应立即降低阈值或增大断层带宽度。更合理的做法是保留当前基线结果，使用新的输出名称启用【防黏连增强】复跑，并通过质量图比较被拆分区域是否主要切掉背景桥，而没有切断真实断层响应。”

### 20.10 第 10 章“配置说明与参数说明”写作要点

参数章节应把参数写成用户能理解的业务语言，而不是内部变量名堆叠。每个参数都要说明默认值、类型、取值范围、是否必填、生效方式和风险。对于解释人员来说，最重要的是理解参数变化会带来什么结果：分位数降低通常会提高召回但可能增加噪声；面积阈值提高会减少碎片但可能过滤小断层；断层带半宽增大会覆盖更宽区域但可能增加近邻黏连风险；防黏连增强会减少错误合并但可能让个别弱连接变得更保守。

本章还应说明配置生效机制。环境变量在启动器启动时读取，INI 配置在下次启动时加载，界面参数在点击【开始追踪】时传给 Runner，命令行参数只对本次运行生效。这样的说明能帮助用户理解为什么改了环境变量但界面没有立即变化，或者为什么上一次界面设置被保存。

参数示例应包括 GeoEast Runner 示例和外部文件示例。正式手册中的示例命令应尽量可复制运行，但密码字段不应写入真实密码。对于高风险参数，必须提供回滚方式。

推荐表格包括系统配置表、业务配置表、安全配置表、集成配置表、核心参数表和风险提示表。正文要强调参数调整必须可回溯，不建议多参数同时大改。

示例文案：

“参数不是为了追求某一个固定结果数量，而是为了在不同数据质量下取得覆盖、分离、闭合和边界自然之间的平衡。正式项目中应先使用推荐预设建立基线，再针对明确问题进行局部调整，并保留每次调整的输出和诊断文件。”

### 20.11 第 11 章“数据管理”写作要点

数据管理章节应说明输入、输出和诊断数据的生命周期。FaultPolyTrace 的输入可能是 GeoEast `BOMapGrid`，也可能是外部 DAT 或 ASCII 网格；输出可能是 GeoEast `BOFaultPolygon`，也可能是 CSV、WKT、JSON 和 PNG。用户需要知道哪些是正式成果，哪些是过程证据，哪些是临时实验文件。

网格导入规则尤其重要。用户已经遇到过同一 `test.dat` 手动导入后显示范围异常的问题，这说明坐标、行列数、采样间隔和空值处理对结果叠合至关重要。文档应明确：如果输入网格头错误，即使算法本身正确，输出多边形也会在 GeoEast 中显示错位、过大或过小。

备份和恢复要面向可回溯交付。正式结果应保留输入说明、输出对象、参数、诊断 JSON、质量图和报告。若误删结果，可从数据库备份、WKT / CSV 或相同参数重跑恢复。删除规则要写警告，避免用户误删正式解释成果。

推荐表格包括核心数据对象表、数据字段表、导入规则表、导出格式表和备份策略表。正文应强调数据权限和脱敏。

示例文案：

“对断层多边形自动追踪而言，输入数据的空间定义与属性值本身同等重要。若行列数、坐标起点或采样间隔错误，结果可能在视觉上表现为一个巨大版面或一个很小的点，这不是算法追踪失败，而是数据空间定义不一致导致的叠合错误。”

### 20.12 第 12 章“报表、查询与分析”写作要点

本章要帮助用户判断“结果好不好”。断层多边形结果不能只用多边形数量评价，也不能只看一张漂亮的叠合图。文档应建立综合评价口径：覆盖率、防黏连、粒度、拓扑、边界贴合和性能共同决定质量。特别要解释强响应覆盖和弱响应覆盖的意义：强响应通常代表主断层或明显断裂，必须尽量覆盖；弱响应可能代表细小断层、端点延伸或噪声，需要结合连贯性和地质合理性判断。

报表章节应说明质量图、面积统计、拓扑诊断、分支诊断和综合评分的作用。面积统计满足赛题要求，但面积不是唯一指标；拓扑诊断保证闭合合法；防黏连指标用于识别错误合并；性能指标用于证明核心算法满足 1 分钟要求。

常见数据口径问题要写得直白。例如“多边形数量不是固定值”“结果断续不一定都是错误”“弱响应没覆盖可能是阈值或面积过滤导致”“边界空隙可能来自平滑或显示比例”。这些解释能减少用户把所有视觉差异都归因于算法错误。

推荐表格包括指标口径表、报表类型表、筛选规则表和常见口径问题表。图示建议放白底叠合图、局部放大图和质量评分示例。

示例文案：

“一个好的结果应同时满足几个条件：主要断层响应被连续覆盖，近邻但不同脉络的断层没有被错误合并，每个多边形闭合且无自交，边界与属性带贴合自然，碎片数量处于解释人员可接受范围内，核心耗时满足性能门禁。”

### 20.13 第 13 章“集成、接口与扩展”写作要点

本章应澄清当前产品的接口形态。许多企业级模板默认有 HTTP API，但 FaultPolyTrace 当前是本地软件和 GeoEast 集成工具，没有公开 REST API。文档要明确“API Base URL 不适用”，同时详细说明命令行接口和 GeoEast Runner 接口。这样既符合模板要求，也避免虚构不存在的 Web 服务。

命令行接口应写清认证方式、必填参数、输出形式、退出码和错误信息。GeoEast Runner 必填数据库、项目、用户、输入网格和输出对象；外部文件模式必填输入文件和输出文件。响应不是 JSON HTTP 响应，而是控制台日志、退出码、输出对象和诊断文件。

扩展说明可以面向未来：如果后续需要接入企业流程平台，可封装命令行；如果需要批量任务，可在 PowerShell 中调度；如果需要平台化，可在现有 Runner 外层增加服务化 API，但这不属于当前版本。

推荐表格包括集成场景表、接口清单、请求参数表、响应说明表和安全建议表。示例应使用 PowerShell 命令，而不是 `curl`。

示例文案：

“当前版本不提供 HTTP API，因此没有 API Base URL、Webhook 或 Postman 调用方式。系统对外提供的是本地命令行接口和 GeoEast 集成接口，用户可通过脚本将其纳入批处理、验收回归或企业内部作业流程。”

### 20.14 第 14 章“系统管理与运维维护”写作要点

运维章节要把 FaultPolyTrace 作为任务型本地工具来描述，而不是常驻服务。启动器只是图形界面，Runner 执行完任务就退出，因此“服务状态检查”应关注程序是否可运行、数据库是否可连、输入是否可读、输出是否可写、日志是否生成，而不是检查某个守护进程。

监控指标应包括运行成功率、耗时、内存、拓扑异常、输出文件生成情况和数据库写入情况。对于批处理场景，可用脚本检查退出码、诊断 JSON 和拓扑指标，并在异常时停止后续任务。

日志和保留周期要写清。正式项目中，启动器日志、Runner 日志、诊断 JSON、质量报告和 GeoEast 平台日志共同构成问题排查证据。运维人员应知道日志在哪里、保留多久、什么时候需要提交给支持人员。

推荐表格包括状态检查表、监控指标表、日志类型表、运维检查清单和容量规划表。高可用和灾备章节应按本地工具特点写备用工作站、发布包、许可证和数据库备份，而不是强行写集群。

示例文案：

“FaultPolyTrace 的可用性不只取决于自身可执行文件，还取决于 GeoEast 运行环境、数据库连接、项目权限和许可证状态。运维检查应覆盖完整链路，而不是只检查程序是否存在。”

### 20.15 第 15 章“安全、合规与审计”写作要点

安全章节要围绕地质项目数据保护展开。断层属性、坐标范围、项目名、结果图和报告都可能属于敏感资料。虽然产品本身不主动上传数据，也不内置云服务，但外部导出和截图传播仍然存在泄露风险。

身份认证和权限控制应明确依赖 GeoEast 和企业账号体系。FaultPolyTrace 应记录任务上下文，但不应保存明文密码。数据导出审计要关注 CSV、WKT、PNG 和报告，因为这些文件比数据库对象更容易被复制传播。

高风险操作说明必须具体。例如覆盖已有输出会导致正式成果混淆或丢失，删除对象会导致无法复查，外发截图可能泄露坐标和项目名称，错误许可证会导致演示功能不可用，过度修改参数会导致质量不可控。每个风险都要对应控制措施。

推荐表格包括高风险操作表、安全最佳实践表和审计字段表。正文应强调最小权限和脱敏。

示例文案：

“正式汇报或竞赛提交前，应检查截图中是否包含敏感路径、用户名、项目名称和坐标范围。若资料需要外发，应按项目保密要求进行脱敏，并保留导出记录。”

### 20.16 第 16 章“升级、迁移与回滚”写作要点

升级章节要服务于可回溯和质量稳定。算法产品升级可能改变默认参数、质量指标、输出多边形数量、边界平滑效果和诊断 JSON 字段。因此升级不能只替换 exe，必须先备份旧版本和基线结果，再用固定数据进行回归验证。

回滚条件要写得可判断。如果新版本无法读取网格、无法写入结果、拓扑异常不为 0、明显漏检、明显误合并或耗时超过门禁，就应回滚。回滚步骤应包括关闭程序、恢复旧文件、恢复配置、使用基线数据验证和保留问题日志。

迁移部分可以说明当前输出对象和文件格式较简单，无复杂数据迁移，但建议升级前后的结果使用不同对象名保存，便于对比。

推荐表格包括升级前检查表、升级影响表、验证表、已知问题表和版本变更记录表。正文应强调“先验证，后启用”。

示例文案：

“算法升级后的结果不一定与旧版本多边形数量完全一致。验收时应重点比较覆盖率、拓扑合法性、防黏连效果、边界贴合和性能，而不是要求每个对象编号和数量完全相同。”

### 20.17 第 17 章“故障排查、错误码与 FAQ”写作要点

故障排查章节应从总流程开始。用户遇到错误时最需要的是知道先做什么：保存日志、截图、输入输出对象、参数和诊断文件，然后按环境、权限、数据、算法、显示五类逐步排查。不要一开始就给大量错误码，否则用户容易迷失。

错误码表应包含错误提示、可能原因、处理方式和是否需要联系支持。对于底层异常，如 `bad allocation`，文档不能简单写“内存不足”，因为在 GeoEast 集成环境中它也可能由环境支撑文件、数据库连接、对象读取异常触发。处理方式应要求用户收集“最后一个 GeoEast 步骤”和完整日志。

FAQ 要覆盖用户真实遇到的问题：平面成图无许可证、菜单入口消失、手动导入 DAT 显示巨大版面、输出颜色看不清、结果断续、近邻断层误合并、输出对象找不到等。每个 FAQ 应避免责备用户，而是解释现象、原因和下一步。

推荐表格包括错误码表、常见问题表和工单材料清单。正文应强调联系支持前准备材料。

示例文案：

“如果结果显示范围明显不对，优先检查输入网格的空间信息，而不是调整算法参数。算法只能在给定网格坐标上生成多边形；如果输入坐标已经错位，输出结果也会随之错位。”

### 20.18 第 18 章“最佳实践与典型场景”写作要点

最佳实践章节要把前面所有规则转化为可执行建议。它应告诉用户面对不同数据应该如何选择预设，如何命名输出，如何判断结果，如何归档证据，如何避免常见错误。这个章节非常适合作为培训和答辩材料。

对于算法质量，应强调默认流程：先用【贴合融合推荐】建立基线，再根据问题选择【防黏连增强】或【弱响应高召回】，最后用质量图和诊断报告判断是否接受。不要鼓励用户无目标地反复调参。对于真实生产，建议每个正式结果都保留基线、候选、最终三个层次，方便解释和审计。

典型案例应覆盖官方赛题数据、近邻黏连数据、弱响应数据、宽断层带数据和外部 DAT 导入数据。每个案例应说明场景特点、推荐预设、检查重点和风险。

推荐表格包括推荐配置表、备份策略表、常见错误做法表和典型案例表。正文应强调产品级应用不是追求某一张图“看起来最好”，而是建立稳定可复用流程。

示例文案：

“正式使用中，好的结果不是由一次幸运调参得到的，而是由稳定输入、合理预设、质量门禁、局部复核和完整归档共同保证。只有当同一流程在多类数据上都能解释得通，才能称为产品级能力。”

### 20.19 第 19 章“附录”写作要点

附录用于放置正文中不宜展开但用户需要查阅的信息，例如术语、缩写、菜单路径、字段说明、配置模板、导入模板、错误码索引、快捷键、图标说明和参考文档。附录应保持简洁、可搜索、可复制。

对于本产品，附录中的配置模板和导入模板很有价值。它们可以帮助用户检查自己的环境是否与示例一致，也可以帮助管理员准备标准导入文件。参考文档清单应使用中文文件名，并与 `docs\文档目录.md` 保持一致。

推荐表格包括术语表、缩写表、菜单路径表、字段说明表和图标说明表。模板内容应使用等宽代码块，避免 Word 自动格式化破坏路径或参数。

示例文案：

“附录中的模板仅作为格式参考，实际项目应根据真实数据库、项目名、输入网格、坐标范围和权限配置填写。复制模板后，必须先在测试项目中验证，再用于正式数据。”

### 20.20 第 20 章“逐章写作要点”写作要点

本章本身应作为文档维护规范。后续若产品升级、参数增加、界面变化或交付对象变化，维护人员应先更新正文，再更新本章对应写作要点，确保文档设计意图没有丢失。对于企业级交付而言，文档不是一次性产物，而是产品能力的一部分。

本章建议采用段落说明为主，表格为辅。原因是写作要点往往涉及判断和取舍，仅靠表格会显得机械。段落中应解释每章为什么重要、要避免什么问题、推荐哪些表达方式。示例文案应尽量可直接复用。

示例文案：

“当软件功能发生变化时，应先判断变化影响的是用户操作、系统配置、数据结构、接口、质量指标还是故障排查。然后更新对应章节，而不是只在发布说明中追加一句描述。只有这样，手册才能保持可用、可信和可审计。”

### 20.21 第 21 章“文档质量检查清单”写作要点

质量检查清单是发布前最后一道门。它应覆盖治理信息、目录导航、操作流程、参数说明、数据管理、接口集成、运维维护、安全合规、故障排查、可搜索性、截图占位和交付一致性。清单中的每一项都应能被实际检查，而不是抽象口号。

对于 Word 版本，还应检查标题样式是否真实、目录是否可更新、表格是否不溢出、正文是否可搜索、页眉页脚是否统一、封面是否完整、截图占位是否明确。对于 PDF 或 HTML 版本，应检查书签、链接和搜索效果。对于竞赛交付，应检查文档是否能直接对应评分项。

推荐表格就是质量检查清单本身。每次发布时，编写人、技术审核人和业务审核人应分别勾选，发现问题后回到对应章节修改。

示例文案：

“文档通过质量检查并不意味着内容永远正确，而是说明当前版本在已知软件能力和交付范围内具备完整性、一致性、可读性和可执行性。后续软件变更必须触发文档同步更新。”
